## 〇、知识库检索复核补充的关键细节（2026-09-22 增补）

1. **confidence ≠ probability，官方自己实测区分**：Choice 选中某项的概率是 0.84，confidence 只有 0.596——前者是"相对其他选项多可能"，后者是"模型对这次判断有多大把握"。**我们做置信度分流时要用 confidence，不是 softmax 最大值**；若走 SemIf 截 logits 拿不到官方 confidence，需要自己映射（如熵值）。
2. **并行采样器**：一份 state 只编码一次，N 个问题共享表示并行算概率，加问题几乎只增输入 token 不增延迟——意味着 SmartFilter 一次请求可同时问"重要吗 / 是营销吗 / 要立即提醒吗"三个问题，不付三倍延迟。
3. **RLCD 校准风险是"官方没证明的那部分"**：无 ECE、无可靠性曲线公开；APUS 复现（Qwen3.5-9B，MIT 协议，`fast-browser-use` Agent Skill）RTX PRO 6000 单次决策 79ms，但校准对齐程度作者自己承认未对齐。**这就是为什么第一步必须自标数据画曲线**。
4. **移动端 A 档场景清单与我们的重合度**：① 通知智能分类免打扰（= 我们的 SmartFilter）② 短信/来电意图识别反诈（= SmsSource/CallLog 侧可加）③ 语音助手前置路由（= 未来语音入口）④ 剪贴板/截图分类。**通知分类被文章列为"现在就能做且价值明确"的第一位**。
5. **风险项对号**：中文场景要打折扣（中/日/韩可用但不均衡，概率校准退化）；判错代价极高的决策与 Sol 差 6–12 个点，别用它兜底；>255 标签要两段式。
6. **上手续表**：第 1 周云 API 跑 A 档场景（建议就从通知分类开始）→ 第 2 周标注 200–500 条画可靠性曲线定三档阈值 → 第 3–4 周接端侧模型跑同批数据对比（重点验 INT4 校准）→ 第 5 周真机矩阵测 P95 延迟/内存峰值/发热。**我们直接从第 2 周开始即可**（端侧模型已在，跳过云 API 验证或用云端快跑一遍做对照基线）。

## 一、Jev 核心结论（对我们有用的部分）

1. **它不是更小的 LLM，是被砍掉"说话能力"的 LLM**：state 进 → Choice（≤255 选 1）/ Score（2–10 级打分）/ Noul（0–1 概率）出。无自回归 decode。
2. **判断和生成的负载形状完全不同**：
   - decode 是内存带宽瓶颈：骁龙 8 Elite NPU decode ≈ 14–42 tok/s；
   - prefill 高并行：同芯片 NPU prefill ≈ 786 tok/s（4B Q4）甚至 11000+（0.5B）。
   - **一次前向判断 ~100ms vs 生成 100 token 3–5s，差 30–50×**。Redacto 实测 Gemma 4 E2B 在骁龙 8 Elite 上 NPU 单步 TTFT 92–104ms——**和我们同款模型**。
3. **手机上做判断比云上更值得**：竞品是"根本跑不动的生成式 LLM"，差距是能不能做。
4. **提问工程 = 决策表设计**：单问 62.6% → 拆 5 个窄问 95.0%。宽泛判断要拆。
5. **confidence ≠ probability**，且中文 + INT4 量化下校准会退化 → 阈值必须用自标数据调，不能抄 0.5/0.85。
6. **推荐架构：反射层（决策）/ 规划生成层 / 执行层（确定性代码）三层分工 + 置信度分流**（高置信自动过 / 中置信标注复核 / 低置信升级上云）。

## 二、项目里"伪装成 LLM 生成的判断"清单（逐条对号）

| # | 现状 | 代码位置 | 本质 | 问题 |
|---|------|----------|------|------|
| 1 | **SmartFilter 通知语义过滤** | `notification/SmartNotificationListener.kt`（`withTimeout(15s)`） | 判断"这条通知重要吗"——封闭 4 分类 | 用完整生成做分类，decode 几十~几百 token，实测 UI 要等十几秒才刷新；15s 超时经常白烧电 |
| 2 | **规则触发 AgentQuery** | `trigger/ActionExecutor.kt`（我们刚加了 120s 全局闸门 + 熔断） | 大部分规则命中后需要的不是"一段话"，是"要不要做/做哪个"的判断 | 一旦命中就起完整生成，正是 P0 自激循环的能耗放大器 |
| 3 | **记忆抽取** | `LocalLLMClient.chat()` 旁路（上一轮修过会话槽位冲突） | Noul 判断"这段对话值得记吗 + 记哪条" | 每轮全量生成；且与主会话抢唯一 conversation 槽位 |
| 4 | **端侧意图路由缺失** | `agent/OnDeviceProfile.kt` 端侧档位 | "这句话是闲聊/工具/复杂任务"是 Choice | 目前 LOCAL 档所有消息都进 8192 窗口生成，简单指令也付全价 decode |
| 5 | **GUI 自动化选点** | `AccessibilityBridge`（11 工具）+ `ScreenSkill`（4 工具） | "屏幕上这些编号元素，点哪个"——正是 APUS `fast-browser-use` 的原题 | 现在靠 LLM 生成坐标/序号文本，慢且易格式错 |

**共性**：全部满足 Jev 的"能做四问"——输入短（<500 token）、答案空间可穷举、判错可回退、无需解释。
**反例（别做）**：主聊天回复本身是生成任务，决策化不适用；ActionExecutor 的删改类不可逆动作不上黑箱自动执行。

## 三、落地路径：不引入新模型，用现有 Gemma E2B 做"决策模式"

我们已有 LiteRT-LM 0.10.0 + Gemma 4 E2B（INT4，窗口 8192）。文章里社区复现的 **SemIf 路线（零训练、截 logits）** 零成本可抄：

```
prefill（系统提示 + state + 决策表，<500 token）      ← NPU/CPU 高并行，~100–300ms
  → 在"答案："处停，读下一 token 的 logits
  → 对选项 token 做 softmax = 各选项概率 + confidence
  → （若 LiteRT 不暴露中间 logits）降级：只 decode 1 个 token 再解析，仍是百 ms 级
```

### 新增 `OnDeviceDecisionProfile`（与 OnDeviceProfile 平行）

- `DECISION_SYSTEM_PROMPT`：只放决策规则，禁止生成性措辞，明确"只输出选项字母"；
- `decide(state, options): DecisionResult(choice, distribution, confidence)`；
- 置信度分流常量：`AUTO ≥0.85 / CONFIRM ≥0.55 / ESCALATE`——**上线前必须用自标数据重定**（中文 + INT4 校准退化是文章点名的坑）。

### 逐项改造点

| 项 | 改造 | 预期收益 |
|----|------|----------|
| P3-1 SmartFilter 决策化 | 15s 生成 → 单次 decide，4 选项：`重要/普通/营销/忽略`；高置信直接进过滤，低置信放行不滤 | 通知列表刷新从 ~10s+ → **<1s**；省掉超时空烧 |
| P3-2 记忆抽取 Noul 门 | 抽取前先 decide"值得记吗"（0–1）；低分直接跳过生成 | 省一轮生成 + **避开 conversation 槽位抢占**（判断也走独立短会话或同锁内） |
| P3-3 规则前置判断门 | AgentQuery 前插 decide"该事件是否需要 LLM"，低于阈值走确定性模板回复 | 在 120s 闸门之上再砍无效生成；进一步压自激能耗 |
| P3-4 意图路由 | 每条消息先 decide `闲聊/工具调用/复杂任务`：闲聊本地短生成，复杂任务提示可上云 | 简单指令不再付 8192 窗口全价 |
| P3-5 GUI 自动化选点 | `read_screen` 候选编号集 → decide 点哪个；执行层仍走 `performAction(ACTION_CLICK)`（避开已知手势自锁隐患） | 生成坐标文本 → 选项分类，格式失败路径归零 |

### 顺带的端侧推理红利（与决策化正交）

- **NPU delegate 排查**：文章实测 NPU 能耗是 CPU 的 1/12.3。查荣耀 DNP-AN00 的 SoC 是否在 LiteRT QNN 支持列表（主要骁龙 8 系），若是则给 LiteRT-LM 试挂 QNN delegate；不是则保留 CPU（llama.cpp 在 Android 上常比 GPU 快，别碰浏览器 WebGPU——prefill 5–15 tok/s 是死路）。
- **输入长度纪律**：决策输入 <500 token 硬线；事件触发（✅ 已是）不做高频轮询，批量任务"处理一条、冷却 60–90s"。

## 四、风险护栏（对号入座文章"七坑"）

1. **校准验证放第一位**：标注 200–500 条自己的通知数据，fp16（云端对照）vs INT4 各画可靠性曲线；校准塌了就只用相对排序、不用绝对阈值——这是上手第一件事，别放最后。
2. **中文阈值单独调**，不照搬英文文档的 0.5/0.85。
3. **长尾设备**：按真机（荣耀 DNP-AN00）实测定预算，别按旗舰数据。
4. **不把决策黑箱用于不可逆动作**（转账/删除类保持人工确认或云端复核）。
5. **需要解释的场景不用**（通知折叠、意图路由都无需解释 ✅）。

## 五、实施顺序

1. **第 1 步**：验证 LiteRT-LM 0.10.0 能否取到 prefill 末 token logits（决定走 SemIf 还是 1-token decode 降级）；同时跑校准标注。
2. **第 2 步**：`OnDeviceDecisionProfile` + SmartFilter 决策化（P3-1，收益最大）。
3. **第 3 步**：P3-2 记忆门 → P3-3 规则门 → P3-4 意图路由。
4. **第 4 步**：P3-5 GUI 选点（前置：先修记忆里三个已定位的无障碍/MediaProjection 隐患）。
5. 全程复用 P1 已建立的端侧档位分离与预算公式（窗口 8192 − 输出预留 768），决策会话用独立小预算即可。

> 一句话：**把生成留给聊天，把判断从 SmartFilter / 规则触发 / 记忆抽取 / 工具路由里剥出来做成决策表，用同款 Gemma 的单次前向（~百 ms）替掉整段 decode（几秒~十几秒）**——这是当前架构下性价比最高的端侧提效项。
